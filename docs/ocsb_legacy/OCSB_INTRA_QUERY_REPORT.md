# 查询集内遗漏条件化自桥接（Intra-Query Selective Bridging）

日期：2026-11-17
状态：**正面结果，Arith 口径显著**

---

## 0. 摘要

把 OCSB 的"外部无标签池 U"换成"查询集 Q 自己"，其余流程（BridgeScorer 挑点、
85/15 槽位、`predict_agg` 相关性融合）完全不变。539 集结果：

| 口径 | Baseline | 自桥接 | Δ | 95% CI | 显著 |
|---|---:|---:|---:|---|---|
| Cumul | 0.3229 | 0.3293 | +0.64 | [−0.07, +1.35] | 边缘 |
| **Arith** | 0.3702 | **0.3795** | **+0.93** | **[+0.26, +1.61]** | **是** |

与跨房间版本的关键差异：**跨房间是 Cumul 显著、Arith 不显著；自桥接是 Arith 显著**。
逐集口径能涨，说明不是类间重平衡，而是每集都真实好了一点。

对照实验（同样池子、同样比例、随机选点）只有 +0.10 Cumul / +0.21 Arith，
证明增益来自 **BridgeScorer 的选点质量**，不是"原型来自查询集自己"这个事实。

---

## 1. 动机

原来的设定是"外部无标签池 U"，有三个问题：

1. **跨房间域偏移**：U 是别的房间的切块，其前景原型与查询目标在不同光照、
   不同家具形态下分布不一致。
2. **协议漏洞**：需要解释"为什么外部池里刚好有当前类别"。标准 FS-PCS 协议
   只保证查询集里有目标，不保证外部池里有。
3. **代码复用**：整套挑点与融合代码本来就是通用的，只把输入从 `uf` 换成 `qf`
   即可。

---

## 2. 实现

与 `v3h_build_cache.py` 的唯一区别是输入块：

```python
# 跨房间：在 uf 上挑
b_sel, c_sel, w, st = pick_protos(model, uf, p0_u, s_fg, s_bg, rev_u, scorer, args, dev)

# 自桥接：在 qf 上挑（qf 需要补一个 seg_d，其余完全相同）
qf['seg_d'] = seg_downsample(qf['xyz'], q['seg'].to(dev), qf['cd'])
p0_q = softmax(predict_agg(qf, [sparse_s], 0.0)[1])[:, 1]
b_sel, c_sel, w, st = pick_protos(model, qf, p0_q, s_fg, s_bg, rev_q, scorer, args, dev)
```

`rev_q` 按训练时的同一定义算：用 `p0_q` 构造的 B 原型反向预测 S，取 S 真前景上的
平均激活。直接传 0 会让 z-score 后的分布偏移。

构造与融合：
```python
sparse_q = cat([bg 100 (p0_q<0.2), b_proto(85), c_proto(15)])
pred = predict_agg(qf, [sparse_s, sparse_q], lam=0.3)
```

## 4. 关键对照：自匹配还是选点质量？

自桥接有一个固有风险：原型来自查询集自己的点，然后去预测同一批点。
被选中的点与自己的簇中心相似度接近 1，可能只是"锐化已有预测"。

对照实验：**同样的池子（`p0>0.7`）、同样的比例（35%）、同样的槽位（85/15）、
同样的邻接约束（0.15m），只把"按 BridgeScorer 排序取 Top"换成"随机取"**。

| 配置 | B_Q 精度 | Cumul | ΔCumul | Arith | ΔArith |
|---|---:|---:|---:|---:|---:|
| 自桥接 + scorer | **0.5161** | 0.3293 | **+0.64** | 0.3795 | **+0.93** |
| 自桥接 + 随机 | 0.4527 | 0.3239 | +0.10 | 0.3723 | +0.21 |

**随机版几乎不涨（+0.10 / +0.21）。**

如果自匹配是主因，随机版也应该涨——它同样用 Q 自己的点、同样的比例和槽位。
它没涨，说明**增益来自 scorer 选出的那批点更纯**（B 精度 0.516 vs 0.453），
而不是"原型来自查询集"这件事本身。

## 5. 与跨房间版本的对比总结

| | 跨房间（U） | 自桥接（Q） |
|---|---|---|
| Cumul | +0.68 | +0.64 |
| **Arith** | **−0.17** | **+0.93** |
| 显著性 | Cumul 边缘显著，Arith 不显著 | **Arith 显著** |
| Q4/Q5 | −1.50 / −1.63 | **+1.37 / +0.84** |
| B 精度 | 0.5644 | 0.5161 |
| 域偏移 | 存在 | **无** |
| 协议漏洞 | 需要假设外部池有目标类 | **不需要** |
| ΔTP | +1640 | **+2288** |

**自桥接的 B 精度反而略低，但效果更好**——说明"原型与查询点同分布"比"原型更纯"
更重要。这是域偏移的直接证据。

## 6. 局限

1. **仍是 1m block 口径**。官方 COSeg 评估用整 scene（20 万点随机采样到 20480），
   我们用的是 1m block。绝对数字不可与论文的 41.78 直接比较。

   **2026-11-17 补充**：整 scene 口径已重跑，见 `OCSB_SCENE_REPORT.md`。两条结论：
   (a) 整 scene 下 OCSB **无效**（Oracle 上限 +0.11pp），因为整 scene 的瓶颈是
   过预测（FP/TP 达 4.98–22.1）而不是漏检（FN 仅占 7%–17%），OCSB 修错了对象；
   (b) block 口径的候选池同样没有官方的「目标类占比 > 5%」过滤，而 1m block 里
   出现一把椅子时椅子占比天然就高，**这个偏差比官方阈值更强**，所以 block 口径的
   0.3229 也不能当作「与论文同口径」的绝对水平。方法增益的相对比较仍然有效。
2. **Cumul 的 CI 跨 0**（下界 −0.07），只有 Arith 显著。两个口径的结论强度不同。
3. **整 scene 的适用性未知**。整 scene 里目标占比极低（<1%），而 B_Q 的原型来自
   `p0>0.7` 的高置信区，尺度可能不匹配。需要在整 scene 上实测。
4. **Q1/Q2 没有增益**（+0.01/−0.16）。自桥接只能在"已经有部分正确预测"的任务上起作用，
   对 baseline 完全失败的任务无能为力——因为它依赖 `p0>0.7` 里有点。

## 7. 复现

```bash
# 全量（8 分片）
python v3i_intra_query.py --per-class 56 --shard $i --shards 8 \
    --pick-mode score --out $CACHE/v3i

# 随机对照
python v3i_intra_query.py --per-class 56 --shard $i --shards 8 \
    --pick-mode random --out $CACHE/v3ir
```

产物：`v3i_s{0..7}.pt`、`v3ir_s{0..7}.pt`。
