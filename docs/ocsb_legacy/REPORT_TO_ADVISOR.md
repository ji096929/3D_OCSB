# 3D-OCSB 第一步验证汇报

日期：2026-11-05
实验平台：COSeg（CVPR 2024）预训练权重，ScanNet v2 val，fold-0 的 20 个 novel 类
规模：cross-scene 504 episodes / same-scene 两批各 335 eps（seed 121-123、131-133）

---

## 一句话结论

**方案的前提成立，但成立条件比方案描述更窄：桥梁集 B 的收益只在"U 与 query 同场景"时显著（Oracle +2.4～3.8pp vs 跨场景 +1.2pp）。端到端只兑现 0.5pp 左右，且不稳定。B 的可分性仍是瓶颈（最高 AUC 0.610），CSR 模块在两种设定下都失效。**

## 一个必须先说清的实现问题

**此前 504 个 episode 的 U 全部来自"其他场景"。**

这是我在最初写采样代码时为防标签泄漏加的硬约束（`scene not in {support_scene, query_scene}`），泄漏检查确实是干净的（U 与 query 场景重叠 0/1512）。但代价是整个实验变成了**跨场景**设定：support 在 scene A、query 在 scene B、U 在 scene C/D/E。

方案里说的"辅助无标签集 U"，在 episodic few-shot 里更自然的理解是与 query 同场景。**这一条我无法替老师确认，需要问。** 但可以确定的是：两种设定下结论差别很大，跨场景设定的天花板低了近 3 倍。

所以之前"24 个信号全死 → 应该换 backbone"这条推理已经不成立——它挂在一个未检验的设定假设上。同场景设定下 `q_p90` 从 0.583 升到 0.610，说明特征还有余地，先榨干再考虑换 backbone。

## 信号的可分性

21 个超点级特征 + 3 个几何/稳定性 + 6 个 block 级聚合 + 二元/三元组合搜索，全部最高 AUC 0.610：

| 信号 | cross AUC | same AUC | 含义 |
|---|---:|---:|---|
| `q_p90` | 0.583 | **0.610** | 超点内点级前景概率 90% 分位 |
| `margin` | 0.615 | 0.602 | `multi_max − base_abs` |
| `multi_max` | 0.561 | 0.597 | 与 support 100 子原型的最大相似度 |
| block 级聚合（6 个） | – | ≤0.693 | 其中 0.826 是样本量伪信号 |

**没有到 0.70。** 但要注意：B 的 precision 在两种设定下都是 ~37%，而 Oracle 增益差 2.75 倍——**说明增益不来自"B 更纯"，而来自"正确的 B 与 query 更相关"**。同场景内空间距离不是机制（偏相关 −0.026），剩下的是同场景外观/材质/布局一致性。

## CSR 模块

两种 U 设定下都失效，这条结论与设定无关：

| η 方案 | Missed-FG Recall | False Recovery | Recovered C Precision |
|---|---:|---:|---:|
| 无负对照 | 0.780 | 0.977 | 0.167 |
| support_D | 0.975 | 0.975 | 0.208 |
| pool_bg | 0.857 | 0.897 | 0.172 |
| combined | 0.891 | 0.978 | 0.165 |

（same-scene 335 eps；cross-scene 数字几乎相同）**false recovery 0.90–1.00，precision 0.16–0.21。** 建议重新设计或直接砍掉，只保留 OASB。

但端到端上 `B + Recovered_C` 反而比纯 B Top-3 好（floor +9.73pp vs +1.64pp），说明 CSR 的价值可能在"增加覆盖"而非"精确恢复"——这个解释还需要 K 扫描的结果来验证。

### 补充：融合算子的方向性验证（已做，两个方向都关了）

原本的假设是"对称融合 `(1-λ)S + λB` 会把 S 已经判对的前景点拉低"，据此设计了非对称算子。实测（同场景 333 eps，掉点 episode 占 34.7%）：

| 指标 | 均值 | 中位数 |
|---|---:|---:|
| ΔTP | −115 | **0** |
| ΔFP | +271 | **+88** |
| ΔRecall | −0.053 | **0.000** |
| ΔPrecision | −0.076 | −0.030 |

**同场景下掉点 58% 是纯 precision 损失，TP 的中位数变化是零**——B 没有成片拉掉真前景，问题是它引入了假阳性。于是：

- **`boost`（只允许 B 增加前景）方向最差**：同场景 +1.40pp，正好放大 FP。
- **`omit`（锁住 S 的高置信正预测）到 τ_s=1.0 时是 +3.80pp，与对称最优 +3.78pp 完全持平**。锁住的是 TP **和** FP，而 baseline precision 只有 0.37；208 eps 时曾读到 +0.37pp 领先，333 eps 归零。
- **跨场景反过来**：TP 损失均值达 **14.6%**（同场景 6.1%），这个假说在跨场景成立；但 omit 最好只有 +2.34pp，仍追不上对称 λ=0.7 的 +2.66pp（178 eps）。

**RSV（用 B 反推 S 的已知标签）**：同场景 `corr(rsv_iou, 真实增益) ≈ −0.01`，门控 τ 从 0 往上扫全部变差（+4.05 → +1.73pp），完全无效。跨场景略有信号（`corr = +0.165`、`fpr corr = −0.220`，τ=0.1 时 +2.15 vs +1.74pp），但幅度在 SE 内。B 能否认出 S 的物体，与它能否补上 Q 的遗漏前景无关——S 和 Q 是不同物体。

**这里有个重要差异**：同场景的错误模式是假阳性，跨场景是"假阳性 + 真阳性损失"并存。两个设定的瓶颈不是同一个东西，同场景上调好的融合参数不能直接搬到跨场景。

### 关于 Same-Scene 设定的定位

老师文档 3.1.1 明确要求"避免支持、无标签和查询集合之间存在重复场景或重叠点云块"。同场景 U（同 scan_name、不同 block、无重叠点）虽然泄漏检查是干净的（U 与 query block 零重叠），但同房间的材质/家具款式一致，属于 **intra-scene context**，不能当作 Scene-Disjoint 主实验报。

建议按**双设定**并列汇报：

| 设定 | 协议 | Oracle | 端到端 |
|---|---|---:|---:|
| Cross-Scene | S / U / Q 来自不同 scan_name（严格 Scene-Disjoint） | +2.13pp（λ=0.5）/ +2.66pp（λ=0.7） | **+1.11pp**（K=5） |
| Intra-Scene Context | U 与 Q 同 scan_name、不同 block、无重叠 | **+3.78pp**（λ=0.5） | **+1.04pp**（K=20） |

后者对应"机器人在一个房间里分割当前块时，房间里已扫描但未标注的其余块天然构成无标签池"，是真实可用的场景，但要明确标注它不是 Scene-Disjoint 协议。
